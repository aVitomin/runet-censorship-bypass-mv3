# Совместимость и миграция старых настроек

MV3 умеет явно проверить совместимые локальные данные старой MV2-установки и
перенести выбранные настройки в текущую схему. Миграция нужна только профилям,
где такие данные действительно существуют; чистая установка её не запускает.

## Модель безопасности

- Сначала выполняется read-only аудит и строится очищенный план.
- Применение начинается только после явного подтверждения пользователя.
- Переносятся только известные поля; неизвестные данные не интерпретируются.
- Исходные MV2-данные не удаляются и proxy settings автоматически не
  применяются.
- Повторный аудит и повторное безопасное применение идемпотентны.
- Конфликт с уже настроенным MV3-полем показывается пользователю; существующее
  значение не перезаписывается молча.
- План, warnings, RPC-ответы и диагностика не должны раскрывать PAC-тело,
  приватные URL или proxy credentials.

## Источники старых данных

Аудит ограничен известными областями `chrome.storage.local` и extension
`localStorage`, включая старые PAC-provider metadata, `pac-kitchen-mods` и
notification preferences. Доступ к `localStorage` выполняет изолированная
offscreen-страница, потому что service worker Manifest V3 не предоставляет этот
API напрямую.

Кэши, черновики UI и произвольные legacy-ключи не становятся доверенными только
из-за того, что находятся в storage.

## Что может быть перенесено

После нормализации и проверки поддерживаются:

- выбранный встроенный provider, если его ключ существует в MV3;
- период обновления и безопасные timestamps;
- site rules и whitelist с однозначной семантикой Direct/Proxy;
- настройка использования provider proxies;
- собственные proxy rows, локальный Tor, Tor Browser и WARP;
- `noDirect` и ограничение собственных методов собственными сайтами;
- поддерживаемые notification preferences.

Структурированные proxy credentials могут остаться только в локальном MV3
state для proxy authentication. Они исключаются из PAC, плана миграции,
событий, ошибок, диагностики и RPC-моделей страниц.

## Что не переносится

- raw/cooked PAC и Firefox-only PAC caches;
- производные IP-to-host caches и старые error buffers;
- несохранённые proxy-editor drafts;
- consent/UI state без точного MV3-эквивалента;
- DNS monkey-patching, runtime API monkey-patching и выполнение PAC-текста в
  JavaScript-контексте расширения;
- старые параметры, для которых нельзя сохранить текущую семантику без
  расширения области маршрутизации.

Новый raw и cooked PAC создаётся текущим workflow и хранится в IndexedDB.
`mv3State` содержит metadata и ссылки на артефакты; legacy inline PAC сохраняется
временно только если недеструктивная миграция артефакта не удалась.

## Порядок действий пользователя

1. Откройте **Advanced → Legacy migration**.
2. Запустите аудит и прочитайте найденные категории и конфликты.
3. Выберите только необходимые совместимые поля.
4. Примените миграцию и повторно проверьте Routing sources, Site rules и Proxy
   methods.
5. Запустите единый workflow **Apply configuration**. Сама миграция не включает
   глобальное управление прокси.

Изменение мигрированного периода PAC не должно неявно менять уже активный
интервал periodic update: такое согласование выполняется отдельным явным
действием.

## Требования к изменениям

Любое расширение mapping должно оставаться field-limited, conflict-aware,
идемпотентным и недеструктивным. Проверяйте как минимум:

- аудит не пишет proxy settings и не удаляет legacy storage;
- secrets отсутствуют в плане, RPC и diagnostics;
- конкурентные изменения MV3 state не теряются;
- повторный запуск не дублирует правила или proxy rows;
- restart service worker не меняет результат;
- после миграции требуется отдельный Apply configuration.
